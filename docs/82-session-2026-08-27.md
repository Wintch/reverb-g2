## 1. Wolfenstein: Cyberpilot (1056970) — works, status "testing" (not guest-ready)

Background, unchanged from `docs/23`'s existing Cyberpilot row (2026-08-21/25): native
Bethesda idTech binary `Cyberpilot_x64vk.exe`, runs under Proton via the Steam global
default (no per-app compat-tool override needed), requires motion controllers (seated mech
cockpit — the game reads hand position, not just a gamepad), and its Proton prefix was
already relocated off NTFS to `~/proton-prefixes-external/1056970` (docs/70's `dosdevices`

a real vr-launcher bug that had been silently costing it 6dof hands.

### 1.1 The recipe

Aircar's seated-6dof head-prediction recipe (`docs/80`, patch 0097) was ported to Cyberpilot
via a new `TITLE_PROFILES` entry in `vr-launcher.py`:

```python
"1056970": {
    "WMR_CONSTELLATION_CONTROLLERS": "1",  # explicit: the game needs 6dof hands
    "SLAM_PREDICTION_TYPE": "2",
    "SLAM_PRED_FREEZE_POSITION": "1",
    "SLAM_PRED_NECK_ARM_MM": "150",
    "SLAM_CORRECTION_SPREAD_MS": "50",
}
```

Same four SLAM knobs as Aircar (gyro-orientation prediction, frozen position, 150mm
neck-arc compensation, 50ms correction spread) — but, critically, **with constellation left
ON**, unlike Aircar/Dreams of Dalí which turn it off. Both `scripts/vr-launcher.py` (this
repo) and `~/vr/vr-launcher.py` (the live tree) carry the identical entry — diffed clean.

### 1.2 The vr-launcher merge bug, found and fixed

Profile selection used to be a flat lookup with no merge:

```python
profile = TITLE_PROFILES.get(_appid, PROFILE_DEFAULT)
```

A title that HAS an entry in `TITLE_PROFILES` but doesn't itself set
`WMR_CONSTELLATION_CONTROLLERS` got **only** its own listed keys — `PROFILE_DEFAULT`
(constellation ON) was never consulted once a title had any profile at all. Cyberpilot's
first profile (SLAM knobs only, no explicit constellation key) fell through to
`jack-in-wayland.sh`'s own 6dof default, which is constellation **OFF** — silently dropping
positional controller tracking for a title that needs hands, with no error anywhere in the
log. This is exactly the class of bug the project's "verify physically" rule exists for:
Monado registered both controllers, the session ran, and nothing on the log side said
"hands are 3dof now."

Fixed to a real merge, `PROFILE_DEFAULT` first so a partial per-title profile inherits the
constellation-ON default instead of losing it:

```python
# Merge OVER PROFILE_DEFAULT so a partial per-title profile still inherits the
# constellation default (ON). A listed title that omits WMR_CONSTELLATION_CONTROLLERS
# would otherwise fall through to jack-in-wayland's 6dof default of OFF, silently
# dropping positional controller tracking (the 2026-08-27 Cyberpilot regression:
# its profile set only the SLAM head knobs and lost 6dof hands).
profile = {**PROFILE_DEFAULT, **TITLE_PROFILES.get(_appid, {})}
```

Cyberpilot's own entry also now sets `WMR_CONSTELLATION_CONTROLLERS=1` explicitly (belt and
suspenders — correct after the merge fix regardless, but self-documenting for the next
reader). Both the repo copy and the `~/vr` copy carry the fix — diffed identical. **Any other
title added to `TITLE_PROFILES` in the future that needs constellation is now safe by
default**, not just Cyberpilot.

### 1.4 Performance / 90fps analysis, and the menu-vs-gameplay correction

Perceived frame rate in gameplay: ~60fps. Monado's log shows `Fake pacer fell behind:
jumped 1 period forward (N total)` roughly **4800-6000 times per session** — the app cannot
consistently hold 90Hz, confirmed by the pacer itself, not just felt. In-game graphics
settings appeared to do nothing to that number ("no le dio bola").

**Correction to a figure from an earlier session**: the "90fps" previously recorded for
this title at display mode 0 was **menu-only**, not gameplay — it needs re-measurement in
actual gameplay before being cited as a real number. This matters because it's exactly the
kind of warm-up/context trap `docs/23` already warns about for other titles (menu vs.
steady-state, first-minute DXVK compilation, etc.) — add it to that list rather than treat
it as new.

Levers toward 90, in the order worth trying:
1. **Render resolution — NOT the display mode.** *(Corrected 2026-08-27 after a follow-up
   investigation; the earlier draft of this doc wrongly named display mode 0 as the lever.)*
   `XRT_COMPOSITOR_DESIRED_MODE` (mode 0 = 2880×1440@90 vs mode 1 = 4320×2160@90) only sets
   the DP **scanout/panel** timing — it does NOT change the per-eye **render** target the
   game draws into, which is why dropping to mode 0 changed nothing the user could see. The
   render target is the headset's fixed factory panel size × a supersample scale, independent
   of the display mode (already documented at T158, `docs/64`: "Monado supersamples 140% by
   default, driven by the panel not the display mode"). The **real** render-load lever is
   **`XRT_COMPOSITOR_SCALE_PERCENTAGE`** — Monado's compiled-in default is **140%** (no
   launcher of ours sets it), which renders 3024×3024/eye; setting it to **100** renders
   2160×2160/eye (1.96× fewer pixels) and was measured elsewhere at **168W → 90W** GPU. Set
   it on the service launch: `XRT_COMPOSITOR_SCALE_PERCENTAGE=100`. Cyberpilot's **own
   in-game render-supersampling toggle also works** (client-side, confirmed 2026-08-25) — try
   both. Its in-game **resolution dropdown is inert** here because xrizer's `IVRSettings` is a
   full stub (`xrizer/src/settings.rs` returns 0/false for every read) — that is why quality
   settings "no dieron bola". FOV reduction is NOT a lever today: Monado exposes no FOV crop
   (checked all 240 debug options, T158) and cropping without shrinking the render target
   saves no fill-rate; a real peripheral crop would need a new Monado patch.
2. **GPU 70% power cap** (`power.conf`'s `GPU_LIMIT_PCT=70`, ~175W). Leading suspect for the
   heavy-title ceiling — `docs/23`'s own Cyberpilot row already measured 166W against the
   175W cap during real gameplay, i.e. the cap was being brushed but not conclusively proven
   to be *the* ceiling. Needs a controlled sweep at 100% GPU (`vr-power-setup.sh
   --gpu-limit`) against real content, which needs a human wearing the headset (unattended
   runs don't render this title's content).
3. **Window visibility.** `docs/23` already tracked and partly retracted a "minimize the
   window" claim for this exact title (`feedback_windowed_default_fullscreen_ab` memory) —
   the user keeps the window focused on purpose because backgrounding it costs audio, a
   documented, deliberate tradeoff, not an oversight.

This whole performance area is heavily pre-documented in `docs/23`'s existing Cyberpilot
row (the fullscreen-30fps lock, the windowed-noisy-60-89fps state, the retracted minimize
claim, the 166W/175W measurement). This session's job was the tracking-recipe fix and the
menu-vs-gameplay correction — **build on the existing row, don't re-litigate the power/focus
findings that are already there.**

## 2. Half-Life: Alyx (546560) — parked

- **Native Linux build** (`linuxsteamrt64/hlvr`): grey panel, crashes/stalls under Monado.
- **Proton build, tried both GE-Proton11-5 and Proton Experimental**: reaches a VR session
  but cycles `BEGIN_SESSION`/`END_SESSION`, delivers 0 frames, panel shows Monado's default
  grey. Root cause of the 0-frame behavior itself is still unknown.

**The real win, and it's permanent**: rebuilding xrizer with its `static-openxr` Cargo
feature (`Cargo.toml:16`, `static-openxr = ["openxr/static"]` — already present in the
crate, simply never invoked in the build before now) removed a loader panic that had been
firing at `openxr_data.rs:126`, a `dlopen()` of `libopenxr_loader.so` that the Proton
container doesn't ship. Building with that feature statically links the OpenXR loader into
`libxrizer.so` instead (confirmed: `target/release/build/openxr-sys-*/out/.../
libopenxr_loader.a` and `libopenxr_loader.so.1.1` present in the rebuilt tree, `libxrizer.so`
relinked). **This is a robustness fix for every xrizer title run under Proton, not an
Alyx-specific patch** — any title that was hitting the same dlopen gap benefits from it too.

**Corrected red herring** (see §5 for the general pattern): the xrizer warning "OpenXR:
Unable to get required Vulkan instance/device extensions size" is **benign**. Aircar, which
works perfectly, emits it on every single launch — confirmed by correlating 57 occurrences
of the line across the day with Aircar sessions specifically. Switching Proton versions on
the strength of this warning was a wasted lever; don't chase it again.

**Known xrizer issues from research** (not yet confirmed as the cause of Alyx's 0-frame
behavior, just the candidate list): xrizer#281 (can't throw objects — skeletal-pose velocity
not implemented), xrizer#160 (`SetDominantHand` crash), xrizer#151 (level-transition crash
on Monado specifically).

**Status: parked**, candidate for the project's "complex per-title fix pass." `docs/23`
already planned Alyx as its own separate/permanent storage tier ("Big titles (Alyx class)",
§Sweep methodology) rather than the rotating download-test-discard pipeline — that planning
still holds; this session is the first time the title was actually launched against the
current stack, and the loader-panic fix is worth keeping even though the title doesn't run
yet.

## 5. Two corrected red herrings

**The benign Vulkan warning** (§2): "OpenXR: Unable to get required Vulkan instance/device
extensions size" fires on every xrizer launch, including Aircar's, which works perfectly.
Do not use its presence to justify switching Proton versions or blaming xrizer's Vulkan
path — it was already ruled out this session by direct correlation against 57 known-good
Aircar launches.

**The dead "Delivered frame" grep**: `grep "Delivered frame" ~/vr/jack-in-wayland.log` reads
**0 even when a title IS actually rendering**, unless `monado-service` was started with
`U_PACING_APP_LOG=debug` — without that flag the log line is never emitted at all, so the
grep is not evidence of anything, positive or negative. This is exactly the trap the
project's cardinal rule exists for (`CLAUDE.md`, "the single most important rule"): **the
human in the headset is the instrument**, not a log grep. Saved to session memory as
`feedback_delivered_frame_metric_false_negative` so it isn't rediscovered from scratch.

Related and also benign: `BEGIN_SESSION`/`END_SESSION` cycling by itself is not a failure
signature — working titles (Cyberpilot, per `docs/23`'s own row) probe, tear down, retry,
and then succeed. Only a session that never gets past that cycle, confirmed by a human
looking at the panel, is actually broken.

blanket "broken" verdicts (`scripts/status-dashboard.py`'s `DEMO_LAUNCHES`, 2026-08-26

  instance of §5's dead-grep false negative; the "broken" verdict holds, but for a specific,
  named, upstream-tracked reason instead of an unexplained "0 delivered frames."

Neither correction has been written back into the dashboard's verdict text yet — this doc

particular currently overstates the case).

## 7. Playlist sequencer (new this session)

A demo-round sequencer that plays a mixed, ordered playlist of experiences — in-house
videos and Steam titles — one at a time, with a spoken cue and a full clean teardown
between each.

**Files**: `~/vr/playlist-runner.py` (the sequencer itself — **not yet copied into this
repo's `scripts/`** [in scripts/ since 3bde463, 2026-08-27], unlike the rest of the toolkit; follow-up needed per the project's own
"sync `scripts/` with the copy in `~/vr/`" rule) and `scripts/status-dashboard.py` (repo
copy, already live — the web integration).

**Protocol**: a control file and a status file, both JSON, polled rather than pushed:
```
control  ~/vr/logs/playlist-control.json : {"command": "run|pause|stop|skip"}
status   ~/vr/logs/playlist-status.json  : live state the dashboard renders
```
Semantics, from the runner's own docstring: `pause` = don't start the next entry (takes
effect at the entry boundary); `stop` = teardown now and end the round; `skip` = end the
current entry now and move on.

**Endpoints** (`status-dashboard.py`): `GET /api/playlist/catalog`, `GET
/api/playlist/status`, `POST /api/playlist/start`, `POST /api/playlist/control`.

**Catalog** (`PLAYLIST_CATALOG`, deliberately small — "only the best," mirroring the
approved rows in `DEMO_LAUNCHES`):
- Video: `/home/iam/Documents/stereo3d-pack/out/dav2_demo` (4 clips confirmed on disk —
  Blade Runner VR180 ×2, Eve of Destruction SBS, Tron Legacy SBS), played via `play360.sh`
  against the whole directory, 3dof.
- Aircar (1073390), 3dof — approved.
- Dreams of Dalí (591360), 6dof — approved.

The default "Ronda automática" fires the catalog in that order with a 6s gap between
entries.

**What was validated**: a 20-second end-to-end test of the video path — teardown, Monado
up, video decoding at a clean 60fps, countdown, clean teardown, spoken "lista la ronda."

**Known caveat, not yet resolved**: chaining `monado-service` restarts between entries is a
documented USB2-fault trigger (`CLAUDE.md`'s companion-hot-reconnect material,
`docs/61`); the inter-entry gap is meant to give the branch a moment to settle, but the
**full mixed round (video → Steam title → Steam title) has not yet been run with a headset
on**. Only the video-only path has a real end-to-end run behind it.

## 8. DoF dashboard addition

The Session card gained a "DoF (head tracking)" row, framed as a property of the current
player × headset combination, not a fixed per-title fact. It reads live from
`monado-service`'s own `/proc/<pid>/environ` via `rig_telemetry.tracking_mode()` — the
same `WMR_SLAM`/`WMR_CAMERAS` env vars `jack-in-wayland.sh` sets per mode, and the same
source of truth `vr-cockpit.py`'s `gather_calibration()` already used (no separate guess
introduced). Maps `WMR_SLAM=1` → 6dof, `WMR_CAMERAS=1` (SLAM off) → controller-tracking-only
("ctrl"), neither set → 3dof; `None` when no session is live.

## 9. Agreed fps measurement protocol

To avoid ever marking a 60fps title "recommended," any fps verdict from here on needs all
of:
1. Measured in **gameplay**, not the menu (§1.4's correction is the reason this is now a
   rule, not just a one-off catch).
2. **100% GPU** — the 70% power cap lifted for the measurement.
3. **Minimum RENDER resolution** via `XRT_COMPOSITOR_SCALE_PERCENTAGE=100` (or lower) — the
   real fill-rate lever. NOT the display mode (`XRT_COMPOSITOR_DESIRED_MODE` is cosmetic
   scanout timing, proven this session to change no render cost). See §1 lever 1.
4. **Minimum in-game graphics settings** — and the title's own render-supersampling toggle
   off (its *resolution dropdown* is inert under xrizer, so don't rely on it).
5. A **Windows baseline of the same title on the same hardware.** If it hits 90 on both
   platforms, the comparison isolates this project's own stack; if Windows itself can't hit
   90 on this title, any Linux number is apples-to-oranges and shouldn't be cited as a
   regression.

Tooling in progress, separate from this session's work: `~/vr/frame-timing.py`, being built
to extract per-step timing (app/GPU/present ms, late/early %, pacer period-jump counts)
straight from Monado's log, so future verdicts don't depend on ad hoc grepping.
