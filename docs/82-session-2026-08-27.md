# 82 — Proton/xrizer triage notes (2026-08-27): static OpenXR loader, benign warnings, fps protocol

Lessons from one triage round over the titles that reached an OpenXR session but delivered
no frames. Per-title status lives in `docs/23`; where a later audit there disagrees with a
status below, `docs/23` wins. The Cyberpilot launcher-profile merge bug and the seated-6dof
recipe applied to it are recorded in `docs/23`'s Cyberpilot row.

## 1. xrizer built with a static OpenXR loader

Rebuilding xrizer with its existing `static-openxr` Cargo feature
(`cargo build --release --features static-openxr`; `Cargo.toml` already had
`static-openxr = ["openxr/static"]`, it was simply never used) removed a loader panic at
`openxr_data.rs:126`: a `dlopen()` of `libopenxr_loader.so`, which the Proton container does
not ship. The feature links the OpenXR loader statically into `libxrizer.so`. This is a
robustness fix for every xrizer title run under Proton, not an Alyx-specific patch. It did
not make Half-Life: Alyx render (Proton GE-Proton11-5 and Experimental both cycle
`BEGIN_SESSION`/`END_SESSION` with 0 frames; native Linux build shows a grey panel). Candidate
xrizer issues for that case, none confirmed: #281 (skeletal-pose velocity, cannot throw
objects), #160 (`SetDominantHand` crash), #151 (level-transition crash on Monado).

## 2. Signals that are not failures

- **xrizer warning "OpenXR: Unable to get required Vulkan instance/device extensions size"**
  is benign: Aircar emits it on every launch (57 occurrences correlated against known-good
  sessions). Do not switch Proton versions because of it.
- **`BEGIN_SESSION`/`END_SESSION` cycling by itself** is not a failure signature. Working
  titles probe, tear down, retry and then open the real session. Only a session that never
  gets past the cycle, confirmed by looking at the panel, is broken.
- **`grep "Delivered frame"` reads 0 even while a title renders**, unless `monado-service`
  was started with `U_PACING_APP_LOG=debug`: without that flag the line is never emitted.
  `app-fps.sh` and any frame-timing script that reads that line (not in this repo) need the same flag.

## 3. Two Unity titles, two different failures

- **The Night Cafe (482390)**: its one launch died inside the OpenXR loader because
  `XR_RUNTIME_JSON` was not set for that process (a launch-options trap). Without correct
  launch options it had not been tested at all.
- **Anne Frank House VR (2877690)**: reaches a real Monado session, abandons it after one
  capability probe and never retries, matching Valve's `unity-xr-plugin` issues #97 and #111.
  An engine-side give-up, upstream-tracked.
- **DOOM VFR (650000)**: early-exits about 9 s after connecting with 0 frames; launch options
  and the ext4 prefix were confirmed fine. That window matches the Basalt
  `Tracker::pop_pose()` teardown segfault (fixed by patch 0104, `docs/06`); `coredumpctl` was not run to confirm
  they are the same event, so check that before building a DOOM-specific theory.

## 4. Agreed fps measurement protocol

A fps verdict needs all of:
1. Measured in gameplay, not the menu (menu-only "90 fps" readings misled for Cyberpilot,
   which runs about 60 fps in gameplay).
2. GPU power cap lifted to 100% for the measurement.
3. Minimum render resolution via `XRT_COMPOSITOR_SCALE_PERCENTAGE=100` or lower. This is the
   real fill-rate lever; `XRT_COMPOSITOR_DESIRED_MODE` only changes scanout timing, and the
   in-game resolution dropdown is inert under xrizer (its `IVRSettings` is a stub), while a
   title's own render-supersampling toggle does work.
4. Minimum in-game graphics settings.
5. A Windows baseline of the same title on the same hardware: if Windows itself cannot hit
   90 fps, a Linux number is not a regression.
