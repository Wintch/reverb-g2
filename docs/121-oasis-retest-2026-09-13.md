# 121 — Oasis/Ignition retest, 2026-09-13: a transient USB crash (fixed by reboot), a new Wayland lease race, and Valve's own "GNOME Wayland unsupported" disclosure

Follow-up to `docs/117`/`docs/119` (2026-09-07/08). Same Oasis build (driver hash
`6c0ad872fcc0ced8de31d6e6b70b4c3ffafcbec9`, unchanged), same rig. Three things happened today,
in order.

## 1. A new, blocking crash — "Failed to open MR USB Device: 6" — turned out to be local state, not Oasis

Before touching Oasis at all, this session spent time testing a Nisuta NS-COUSBL2 USB
Bluetooth dongle (unrelated side quest — see the assistant's own memory for that thread; short
version: the dongle turned out dead/non-enumerating, and a separate device that looked like it
at first was actually an already-installed DaVinci Resolve license dongle). That testing
involved repeated USB connect/disconnect cycles, including the headset itself dropping and
being reconnected more than once.

With the headset back up (5/5 USB devices) and Oasis re-launched, `vrserver.txt` showed a new,
immediate crash — not the X11 segfault or the Wayland watchdog from `docs/117`/`119`, a third
one, ~2.7s after the driver loaded and found the real hardware:

```
oasis: Found HMD: HP Reverb Virtual Reality Headset G2
oasis: HMD has Sensors FW: 1.9.53
...
oasis: Found presence device: \\?\HID#vid_03f0&pid_0580&mi_00#...
...
oasis: Fatal error: Failed to open MR USB Device: 6  Origin: usbStatus == Result_Ok
  Source: D:\a\WMR-Standalone-Oasis-Driver\WMR-Standalone-Oasis-Driver\driver_oasis\HmdDriver.cpp:4681
```

Win32 error 6 is `ERROR_INVALID_HANDLE`. Reproduced 3/3 times, including after SteamVR's
built-in crash safe-mode was manually cleared via Manage Add-ons each time (see §1a on why
that's needed every single time, not just once).

**Root-caused by elimination, not inspection** (no logs from inside Ignition's Wine-hosted
server process were available to confirm directly): a **full machine reboot** made the exact
same launch sequence succeed cleanly — same driver version, same USB topology, same settings —
with no crash, reaching `Active HMD set to oasis.8CC044Z2CM` every time afterward (3/3). The
most likely explanation is that today's unusually heavy USB churn (dongle testing, headset
disconnects) left some stale device-path/hidraw-handle state that Ignition's Wine-hosted HID
bridge had cached from an earlier, now-invalid enumeration — consistent with `ERROR_INVALID_HANDLE`
specifically. **Not confirmed at the source level, but empirically solid**: 3 failures before
the reboot, 3 clean loads after, nothing else changed.

**Lesson for next time**: if Oasis (or any Ignition-hosted driver) throws a `Failed to open ...
Device` fatal error and the session has had heavy USB device churn (dongles plugged/unplugged,
the headset itself dropped and reconnected), try a full reboot before assuming it's a code
regression. This is now a second entry in the same general bucket as
`reference_g2_usb_port_fault` in the assistant's memory — a USB-churn-sensitive symptom that
isn't really about the code that's failing.

### 1a. SteamVR's crash safe-mode survives both `steamvr.vrsettings` edits and a full reboot

Editing `blocked_by_safe_mode` to `false` directly in `steamvr.vrsettings` does **not** stick —
`vrserver` re-derives the decision fresh at every startup from some other persisted state
(not found in `steamvr.vrsettings`, not found anywhere under `~/.steam/debian-installation/
config/` by a recursive grep for `lastCrash`/`CrashTimestamp`/`safe_mode`) and silently
overwrites the edit within the same launch. **This state also survives a full machine reboot** —
after rebooting specifically to get a clean USB/Wine state (§1), the very first launch attempt
was *still* blocked by a safe-mode event from before the reboot. The only mechanism that
actually works is the GUI: SteamVR Settings → **Manage SteamVR Add-Ons** → **Unblock** (or
**Unblock All**) next to the affected driver(s), then relaunch. Screenshotted live via
`import -window <id>` over Xwayland (see the assistant's own memory for the screenshot-tooling
notes) — the dialog reads literally *"Due to a recent crash, some SteamVR Add-Ons have been
automatically blocked."* Worth remembering: **this has to be redone after every real crash**,
not just once per session.

## 2. Valve's own "SteamVR for Linux Support" page changes the frame for everything in docs/117

The user was redirected here mid-session (`help.steampowered.com/en/faqs/view/18A4-1E10-8A94-3DDA`),
pasted in full. Key sentence, verbatim:

> "Unfortunately not all Wayland compositors support DRM leasing... Notably, Gnome Wayland, the
> default desktop environment for Ubuntu, **is not supported** as it does not support DRM
> leasing. Users using Gnome Wayland will need to switch to an alternative window manager/
> compositor in order to use SteamVR."

Valve lists X11, KDE Plasma Wayland, and wlroots-based compositors (Sway, LabWC, Hyprland) as
the supported alternatives. **This is Valve's own compositor** (`vrcompositor`, part of
SteamVR itself, not something Ignition/Oasis ships) — so this disclaimer applies to Oasis only
because Oasis is loaded *by* SteamVR's compositor, same as any other SteamVR driver would be.

This directly reframes `docs/117`'s "Wayland gets further than X11" finding from 2026-09-07/08.
It was real (direct mode + native 90Hz did briefly work under Wayland that night), but per
Valve's own documentation GNOME/Mutter Wayland is a fundamentally unsupported configuration for
`vrcompositor`'s DRM-leasing code — today's result (below, §3) is consistent with that being a
race that can go either way, not a working path we broke.

## 3. Today's Wayland retest: direct-mode acquisition itself now fails, and we could independently prove the lease WAS available

Same launch sequence as `docs/117`'s successful night (GNOME Wayland, driver_monado disabled,
camera disabled, no `forcedDriver`), but this time `vrcompositor.txt` never reaches "Direct
mode: enabled" — it fails one step earlier than the whole camera/watchdog saga from `docs/119`:

```
Direct mode features: present
HMD deviceUUID is 910695f0d1d3e8a0
Tried to find direct display through Wayland: (nil)
CHmdWindowSDL: Failed to create direct mode surface
CHmdWindowSDL: VR requires direct mode.
Failed to start compositor: VRInitError_Compositor_CannotDRMLeaseDisplay
```

Reproduced **3/3** across independent launches — including one deliberately primed by first
running `jack-in-wayland.sh` (our own Monado stack) to successfully acquire and then cleanly
release the same lease immediately beforehand, to rule out "compositor not ready yet." That
priming made no difference.

**Independently confirmed the lease genuinely was available at the time of each failed
attempt**, via two different tools that are NOT Ignition/SteamVR:
- `reverb-g2/scripts/check-lease.sh`: confirms the kernel side marks the connector
  `non-desktop=1` with 3 modes, and the compositor announces `wp_drm_lease_device_v1` offering
  exactly connector `DP-1`/`HPN` (id 130).
- Monado's own `jack-in-wayland.sh` run in step 1 above: got `DEBUG [_lease_fd] Lease granted`
  cleanly, same session, same connector.

So the failure is specifically in **how Ignition/SteamVR's own `vrcompositor` binds and queries
the `wp_drm_lease_device_v1` global** — not a matter of the lease not existing. This is the
same *class* of bug already tracked upstream against Monado itself:
`project_monado_upstreaming`'s note on issue #614 (`direct_wayland: miss HMD connector due to
insufficient roundtrips` — one `wl_display_roundtrip` after binding the registry can race ahead
of the connector's own `connector`/`done` events). It's plausible Valve's/Ignition's compositor
code has an analogous under-roundtripped query, which would also explain why `docs/117`'s one
success and today's three failures aren't a contradiction — a race that sometimes wins.

**Not investigated further this session**: no source access to `vrcompositor`'s Wayland lease
client code (Valve's, closed-source) to confirm the roundtrip theory directly.

## 4. X11 retest: same wall as `docs/119`, but no crash this time

Switched to GNOME on Xorg, freed the panel from the desktop first this time
(`xrandr --output DP-0 --off`, then the 8s wait `jack-in.sh` already knows is needed before
Vulkan direct-mode acquisition — see that script's own comment on `vkAcquireXlibDisplayEXT`
racing the CRTC teardown), then launched SteamVR. Result: **identical symptom to `docs/119`**
— correctly finds the RandR output, selects `4320x2160@90Hz`, then:

```
Tried to find direct display through RandR: 0x55c2b94bff40
Selected mode 1.
Failed to acquire xlib display
CHmdWindowSDL: Failed to create direct mode surface
Failed to start compositor: VRInitError_Compositor_CannotDRMLeaseDisplay
```

**Difference from `docs/119`: no segfault this time** — `journalctl -k` shows no crash at all,
clean `VRInitError_Compositor_CannotDRMLeaseDisplay` return instead of a SIGSEGV in
`libnvidia-glcore.so`. Either today's Ignition/Oasis build (same driver hash, but Ignition's
own repo had commits land 2026-09-06/10/11 since `docs/117`) hardened this path against
crashing, or it's the same non-determinism as §3 landing on the non-crashing branch this time.
Either way: **the underlying block (can't acquire NVIDIA's direct-mode display) is unchanged**
on X11 too.

## Where this leaves the Oasis/Ignition track

Both desktop paths now have solid, repeated (3/3 each) evidence of failing at the exact same
conceptual step — acquiring exclusive display access for direct mode — via two different,
backend-specific symptoms. Per Valve's own documentation (§2), Wayland-under-GNOME is not a
supported configuration for this at all; X11 is supposed to be supported, and yet fails
identically to before. This NVIDIA+G2 pairing was never one of Ignition's dev's own tested
configurations (only AMD+G2 and NVIDIA+Odyssey+ — see `docs/117`). Nothing here points to an
easy fix from our side. `docs/119`'s draft upstream report has been updated with all of this
(still not filed — the same review-before-submitting stance as before, now with much stronger
evidence attached).

**Not evaluated**: a wlroots-based Wayland compositor (Sway/Hyprland/LabWC) or KDE Plasma, both
of which Valve's page lists as actually-supported alternatives to GNOME Wayland. That's a real,
untried option if this project wants to keep pushing on Oasis rather than parking it — but it's
a bigger lift (new DE, unknown interaction with the rest of this rig's Wayland-only production
pipeline) than anything tried today.
