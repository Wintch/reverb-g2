# MR 1 — source branch `wmr-camera-stop-drain` → monado/monado `main`

## Title

d/wmr: Make wmr_camera_stop() wait for the in-flight transfers

## Description

`wmr_camera_stop()` cancels the camera's image transfers and returns at once. libusb cancellation is asynchronous, so the USB thread can still be inside `img_xfer_cb()` pushing a frame when the caller, `wmr_source`'s `break_apart`, continues with the teardown of the frame context. In `wmr_hmd_create()` the SLAM tracker node is added after the camera source node, and `xrt_frame_context_destroy_nodes()` walks the list head first, so the tracker is broken apart before the camera and destroyed before `wmr_camera_free()` runs: an in-flight callback lands in a tracker that is already gone. On an HP Reverb G2 that is a SIGSEGV in the USB thread on session teardown (`img_xfer_cb` → `xrt_sink_push_frame` → the SLAM receive path, main thread inside `wmr_source_stream_stop`), seen on 20+ coredumps over several days of repeated game start/stop cycles.

c236c11f (!2937) made the callback return early once `running` is false, which covers callbacks that start after the stop, but not the one already past the check when `running` flips. That callback also resubmits its transfer at the end, after the cancel loop found nothing to cancel, which leaves a transfer in flight on a camera that has been told to stop. 8ed03a5c (!3005) made `running` actually true, so both paths are live on `main`.

First commit: count the submitted transfers and have `wmr_camera_stop()` wait, after cancelling, until each has had its final completion. The callback decides between resubmit and retire under the same lock that guards `running`, so a stop landing mid-frame retires the transfer. When `stop()` returns no callback is executing and the transfers are idle, which is also what `libusb_free_transfer()` in `wmr_camera_free()` requires. The wait is bounded (500 × 1 ms, then a warning), following `uvc_fs_stream_stop()`. The USB thread is not touched: it is started in `wmr_camera_open()`, joined in `wmr_camera_free()`, and is what delivers the completions this waits for, so start/stop stay repeatable. A dedicated mutex is used rather than the thread helper's, to keep "what this lock guards" self-contained.

Second commit, separate and independent: the trailing `os_thread_helper_wait_locked()` after the USB thread's loop (upstream's own `@todo`) can hang `wmr_camera_free()`'s join forever if `stop_and_wait()`'s single signal arrives while the thread is still returning from `libusb_handle_events_completed()`. Dropped; it guards no state. Happy to move it to its own MR if preferred.

Scope: `wmr_camera.c` is shared by every WMR headset; nothing in the change depends on the camera count or configuration, but only a G2 was available.

Testing: 120 separate `monado-cli probe` processes on a G2 with SLAM enabled (each one creates the HMD, starts the camera stream, and destroys everything, so both `wmr_camera_stop()` and the `wmr_camera_free()` join run every time): 40 on unpatched `main` `09741cbc`, 40 on an interim version of this change, 40 on this exact one. 0 SIGSEGV, 0 hangs, "WMR camera started/stopped" in every log, and no "still in flight" warning in any run. The unpatched baseline did not crash in this harness either: the window is narrow and the lab hit it under real game sessions, so the argument for the fix is the one above, not the counter.

# MR 2 — source branch `euroc-playback-cam-count` → monado/monado `main`

## Title

d/euroc, st/prober: Size the SLAM tracker by the cameras actually played back

## Description

`EUROC_CAM_COUNT` lets the EuRoC player stream fewer cameras than the dataset holds, but the SLAM tracker created around the player was still sized from `dataset.cam_count`, in both `euroc_run_dataset()` (`monado-cli slambatch`) and `p_factory_ensure_slam_frameserver()` (the service with `EUROC_HMD`). The tracker only flushes poses and submits a frame set once the frame for its last camera arrives, and that camera is never pushed. Both lines come from c39dc977c, the commit that introduced the variable.

Use `playback.cam_count`, which `euroc_player_fill_default_config_for()` already resolves to the dataset count when the variable is unset, so nothing changes for anyone not setting it.

Reproduced with `monado-cli slambatch` on a four-camera HP Reverb G2 recording, `EUROC_CAM_COUNT=2`, Basalt as the VIT system: before, the tracker is created with `cam_count=4` and Basalt stops on the first frame set (with a two-camera calibration on its `calib_cam_count == cam_count` assert; with the four-camera calibration it had been waiting on "Expected cam2 frame, received cam0"). After, `cam_count=2` and the dataset plays to the end (2842 tracking rows, exit 0).
