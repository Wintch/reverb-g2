# 101 -- The Dali dark-panel incident (2026-09-05 noon): presence.conf's "disabled" was bypassed, not a hardware fault

**Status: root cause CONFIRMED with direct log evidence (not a guess).** Fix APPLIED to
`jack-in-wayland.sh` (both `~/vr/` and this repo's `scripts/`, kept in sync). **Fix is NOT yet
live-tested** -- needs a real `jack-in-wayland.sh down` + `up` + a session that again exports
`WMR_USER_PRESENCE=1`, ideally with a real wearer, to confirm the bypass is closed and nothing else
regressed. The separately-tracked RESTORE-is-broken bug (`docs/98`) is NOT fixed by this and is
untouched here -- see "What this does NOT fix" below.

## The incident, in one paragraph

During a live Dreams of Dali (appid 591360) 6dof session launched via `~/vr/vr-launcher.py` with
`VR_LAUNCH_APPID=591360 WMR_USER_PRESENCE=1`, the headset panel went dark mid-session while
`monado-service` kept running and delivering frames on schedule (no crash, steady ~11ms pacer log).
`/sys/class/drm/card0-DP-{1,2,3}/status` all read `disconnected`, `scripts/hmd-connector.sh` came
back empty, and `scripts/panel.py activate` reported full HID-level success (valid EDID-like reads)
without DP ever coming back. USB stayed a healthy 5/5 throughout -- never dropped. The operator's
own note going in was that this *should* have been impossible: `~/vr/presence.conf` has
`PRESENCE_ENABLE=0`, believed to fully disable the newer presence/auto-standby feature. **That
belief was wrong, and this doc is why.**

## Classification against `docs/22`'s fault taxonomy

This is **not** `docs/22` step 4's genuine hardware DP-dead fault. Discriminators, per that doc's
own decision tree:

- Step 0's test (`panel.py activate`, look for the logo) **succeeded** -- "full activation + screen
  on", valid reads. Step 4 requires **no logo at all** after a clean activation; that never happened
  here.
- USB stayed 5/5 the entire time. None of the marginal-visor-connector signatures elsewhere in
  `docs/22` appeared (no `error -71`, no `reqCmd 23`, no HID read failures, no device-number churn).
- `monado-service` never crashed and never failed to construct the HMD device -- a genuine hardware
  DP-dead fault fails much earlier, at compositor/Vulkan init (`XRT_ERROR_VULKAN` / no leasable
  connector), not mid-session after frames were already flowing.

This **is** `docs/22` step 4 point 4 / the "Reseating mid-session (2026-08-10)" pattern: **a stale
DRM lease.** Same signature `docs/98` §2 already documented hours earlier the same day (a different,
Aircar-based incident, early morning): `panel.py activate` succeeding at the HID layer while
Monado's own DRM lease on the connector stays dead, because the two are separate channels and
Monado's compositor has no code path to notice or recover from a lease it already lost. The fix that
worked live -- kill `monado-service`, `rm -f /run/user/1000/monado_comp_ipc`, relaunch fresh -- is
exactly `docs/22`'s documented fix for this signature, applied correctly.

**No physical cable check is warranted from this incident.** Nothing here points at the visor-end
connector or the marginal-contact family of faults documented elsewhere in `docs/22`.

## Root cause, with the exact log lines that prove it

### 1. Monado's own log shows the trigger: presence-driven auto-standby fired

`~/vr/jack-in-wayland.prev.log` (the pre-relaunch log, i.e. the actual incident):

```
  8: INFO [wmr_hmd_create] User presence enabled (WMR_USER_PRESENCE=1): surfacing the companion
     proximity sensor as XR_EXT_user_presence. Threshold is provisional, see wmr_hmd_update_inputs().
...
58101: INFO [wmr_hmd_update_inputs] User presence: panel blanked by auto-standby (120000 ms NOT WORN)
```

No `WORN`/`NOT WORN` committed-transition line ever appears before line 58101 -- meaning the
proximity sensor read "not worn" from the very start of this device's life in the session (the
struct's zero-initialized default), and 120 seconds later the untested auto-standby feature blanked
the panel exactly as designed. **No `panel restored` line ever appears afterward either** -- same
open RESTORE-never-fires symptom `docs/98` §1 already flagged as broken-not-just-unvalidated, now
seen a second time on a different game and a different code path into the trigger.

### 2. That HID-level panel power-down really did drop DP, and mutter noticed correctly

The same log, `comp_window_direct_wayland.c`'s listener, ~2000 lines later (line 60266, right after
three back-to-back `vk_swapchain_present: VK_ERROR_UNKNOWN` errors):

```
DEBUG [_lease_finished] Lease has been closed
```

This is mutter's own `wp_drm_lease_v1.finished` event, delivered to Monado because the connector
genuinely went electrically dark (per `docs/22`'s own anatomy: HPD is generated by the *powered*
ANX7530 bridge -- commanding the panel/bridge off via HID, which is exactly what
`screen_enable_func(wh, false)` does, legitimately drops HPD without touching USB at all). This is
why `dmesg -T` and `journalctl -k` found nothing: nothing here is a USB event, and NVIDIA's
proprietary DRM/modeset driver evidently does not log this connector-status transition to the kernel
ring buffer the way an open-source DRM driver would. `journalctl --user -u org.gnome.Shell@wayland`
(mutter's own log) is equally silent for the whole window -- mutter revoking a lease it granted, in
response to a real HPD drop, apparently isn't logged at its default verbosity either.

Read together with `src/xrt/compositor/main/comp_window_direct_wayland.c`'s own code: `_lease_finished`
just sets `lease->finished = true`, closes the fd, and stops -- the function has a literal comment,
`/* TODO handle graceful shutdown if lease is currently used */`. Nothing re-requests a lease.
Nothing tears the render loop down either: `comp_target_swapchain`'s fake-vblank pacing thread
(`COMP_TARGET_FORCE_FAKE_DISPLAY_TIMING`, set when this target is created) keeps ticking on its own
internal clock regardless of whether anything is actually reaching a screen -- which is exactly why
`monado-service` kept producing "Delivered frame" log lines on a steady ~11ms period, with no crash,
the whole time the panel was dark. This lease-recovery gap is the *only* DRM-lease code in Monado
(grepped `~/vr/monado` for `_lease_connector_withdrawn` / `_drm_lease_device_drm_fd` /
`_lease_connector_done` / `_lease_fd` -- all four live in this one file, `comp_window_direct_wayland.c`,
573 lines total) -- there is no separate idle timer, VT-switch handler, or power-management path in
the compositor itself; the lease is acquired exactly once, at `comp_window_direct_wayland_init`
(`init_pre_vulkan`), and never revisited.

### 3. Why `presence.conf`'s `PRESENCE_ENABLE=0` didn't stop this: a real script bug, not user error

`~/vr/presence.conf` (untracked, mtime 2026-09-05 04:21, set earlier the same day per `docs/98` §1's
"consequence, applied immediately"):

```
PRESENCE_ENABLE=0
PRESENCE_SCREENOFF_MS=120000
```

`jack-in-wayland.sh`'s old logic (identical in both `~/vr/jack-in-wayland.sh` and this repo's
`scripts/jack-in-wayland.sh` -- confirmed byte-identical before this fix):

```bash
PRESENCE_ENABLE_VAL="${WMR_USER_PRESENCE:-${PRESENCE_ENABLE:-0}}"
PRESENCE_SCREENOFF_VAL="${WMR_USER_PRESENCE_SCREENOFF_MS:-${PRESENCE_SCREENOFF_MS:-0}}"
```

**`PRESENCE_SCREENOFF_VAL` was computed completely independently of `PRESENCE_ENABLE_VAL`.** There
was never any code that zeroed `PRESENCE_SCREENOFF_VAL` when `PRESENCE_ENABLE` (from the conf file)
was `0`. The conf file's `PRESENCE_SCREENOFF_MS=120000` was applied unconditionally as long as
`WMR_USER_PRESENCE_SCREENOFF_MS` wasn't separately set in the ambient environment -- regardless of
`PRESENCE_ENABLE`.

Today's Dali launch exported `WMR_USER_PRESENCE=1` in the ambient environment (per the operator's
own launch command, presumably just to get `XR_EXT_user_presence` telemetry surfaced -- a
reasonable, unrelated ask). Because of the `${WMR_USER_PRESENCE:-...}` fallback, that ambient export
wins over `presence.conf`'s `PRESENCE_ENABLE=0` for the purposes of *this specific variable* (by
design, documented in the script's own comment: "Ambient exports win over the conf file, same
pattern as VR_PROFILE/EYE_HEIGHT above"). But `PRESENCE_SCREENOFF_VAL` never checked `PRESENCE_ENABLE`
at all -- so `presence.conf`'s `PRESENCE_SCREENOFF_MS=120000` rode along for free, and the
120-second auto-standby fired on a session everyone believed had it fully disabled.

**This is a structural bug, not a one-off mistake**: `PRESENCE_ENABLE=0` in `presence.conf` was
never actually wired to gate `PRESENCE_SCREENOFF_MS`'s effect in the first place. It only happened
to look like a working "off switch" in every previous test because nobody had separately exported
`WMR_USER_PRESENCE=1` in the ambient environment while it was set to `0`.

## Fix applied

`~/vr/jack-in-wayland.sh` and `~/Documents/reverb-g2/scripts/jack-in-wayland.sh` (kept byte-identical,
per the standing note that these two copies can drift -- see
`reference_jack_in_script_duplication` memory) both changed, around the `PRESENCE_SCREENOFF_VAL`
computation:

```bash
PRESENCE_ENABLE_VAL="${WMR_USER_PRESENCE:-${PRESENCE_ENABLE:-0}}"
if [ -n "${WMR_USER_PRESENCE_SCREENOFF_MS+set}" ]; then
    PRESENCE_SCREENOFF_VAL="$WMR_USER_PRESENCE_SCREENOFF_MS"
elif [ "${PRESENCE_ENABLE:-0}" = "1" ]; then
    PRESENCE_SCREENOFF_VAL="${PRESENCE_SCREENOFF_MS:-0}"
else
    PRESENCE_SCREENOFF_VAL=0
fi
```

Behavior, verified with a standalone bash simulation (three scenarios, not yet against the real
script end to end):

| Scenario | ambient `WMR_USER_PRESENCE` | ambient `WMR_USER_PRESENCE_SCREENOFF_MS` | conf `PRESENCE_ENABLE` | conf `PRESENCE_SCREENOFF_MS` | Result |
|---|---|---|---|---|---|
| Today's bug, repeated | `1` | unset | `0` | `120000` | **`0` -- auto-standby now suppressed** |
| Deliberately opted in via the conf file | unset | unset | `1` | `120000` | `120000` -- feature still works when actually wanted |
| Explicit ambient override for a quick test | (any) | `5000` | `0` | `120000` | `5000` -- ambient override still wins outright, unchanged |

`WMR_USER_PRESENCE` itself (which gates whether `XR_EXT_user_presence` telemetry is surfaced at all,
inside Monado) is untouched by this fix -- an operator can still ask for that telemetry without
silently re-arming the untested auto-standby side effect. `bash -n` syntax-checked both copies;
`diff` confirmed the two copies are still byte-identical after the edit. The currently-running
`monado-service` (PID checked live before and after, never touched) is unaffected -- per the
script's own existing comment, a `presence.conf`/script change only takes effect on the *next*
`jack-in down` + `up`, never live.

## What this does NOT fix, and what still needs a live check

- **The RESTORE-never-fires bug from `docs/98` is untouched.** Today's incident shows the exact same
  symptom (no `WORN`/`panel restored` line ever appears after the blank) on a second, independent
  trigger path. This doc adds a data point to that open bug, it does not close it. Until RESTORE is
  actually fixed, `PRESENCE_SCREENOFF_MS` firing at all -- by any path -- still means an operator
  has to manually kill+relaunch to recover, exactly as `docs/98` §3 already prescribes.
- **This fix has not been exercised live.** The three-scenario table above is a standalone bash
  simulation of the exact snippet, not a real `jack-in-wayland.sh down` + `up` + launch. Next time
  anyone launches with `WMR_USER_PRESENCE=1` set (for telemetry or otherwise), confirm
  `WMR_USER_PRESENCE_SCREENOFF_MS` actually arrives at `monado-service` as `0` (e.g.
  `tr '\0' '\n' < /proc/<pid>/environ | grep SCREENOFF`) and that no `panel blanked by auto-standby`
  line appears in a session left idle/unworn past 120s.
- **Whether the wearer genuinely wasn't detected as "worn" for the first 2 minutes, or whether the
  proximity sensor/companion channel was flaky, is not distinguished here** -- no raw proximity
  values are logged, only committed transitions, same limitation `docs/98` §1 already noted. Not
  investigated further in this doc since it doesn't change the fix (the screenoff path is now gated
  correctly regardless of why the sensor read NOT WORN).

## 2026-09-05, later same day — fix VALIDATED live

Relaunched Dalí with `WMR_USER_PRESENCE=1` (matching the original incident's exact launch
condition), left the headset genuinely un-worn (not touched, on the desk) for 2:30 (past the
`presence.conf` `PRESENCE_SCREENOFF_MS=120000` threshold), with `PRESENCE_ENABLE=0` unchanged from
its existing safe-default value. Result: **`card0-DP-2` stayed `connected` throughout, no "panel
blanked by auto-standby" line ever appeared in `jack-in-wayland.log`** — before this fix, that
exact combination (real not-worn time past the configured threshold, `WMR_USER_PRESENCE=1` set)
reliably triggered the blank/lease-loss bug this doc describes. Confirms the gating fix in
`jack-in-wayland.sh` (both copies) works as intended: `PRESENCE_ENABLE=0` now actually suppresses
`PRESENCE_SCREENOFF_MS`, closing the bypass.

**Not closed by this**: a second, distinct trigger for the same lease-loss symptom was found the
same day, unrelated to this bug (fired ~20s after launch, far too soon for the 120s timer) — see
`docs/100`'s "Recurring DP/lease drop, second distinct instance today" section. This fix addresses
only the presence-screenoff bypass; the other trigger is still unexplained.
